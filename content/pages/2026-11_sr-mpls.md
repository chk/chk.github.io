RSVP-TE hat jahrelang brav seinen Dienst getan. Irgendwann schaut man dann aber mal genauer in die RSVP-Sessions und stellt fest: Bandbreite wird keine reserviert (`0 bps` überall), explizite Pfade gibt es auch nicht, und bei gleich teuren Pfaden würfelt CSPF einfach einen aus. Hin über den einen Router, zurück über den anderen. Im Grunde nutzt man RSVP also nur, um Labels zu verteilen und Fast Reroute zu haben. Genau das kann Segment Routing mit TI-LFA auch – nur ohne extra Signalisierungsprotokoll und mit ECMP geschenkt dazu.
 
Da bei mir sowieso ein Plattformwechsel von Junos auf EOS anstand, habe ich beides kombiniert. Ausgangslage: OSPF als IGP, ein Full Mesh aus RSVP-LSPs mit Facility Backup, L3VPN obendrauf. Ziel: IS-IS mit SR-MPLS und TI-LFA.
 
Alle Adressen und AS-Nummern hier stammen aus den Dokumentationsbereichen ([RFC 5737](https://www.rfc-editor.org/rfc/rfc5737), [RFC 5398](https://www.rfc-editor.org/rfc/rfc5398)). Loopbacks sind `192.0.2.<n>/32`, Core-Links `/31` aus `198.51.100.0/24`.
 
### Erst das Protokoll, dann die Hardware
 
Die wichtigste Erkenntnis vorweg: Man will die neuen Router auf keinen Fall noch als RSVP-Knoten einbinden, nur um RSVP danach wieder abzuschaffen. Also wird erst auf der alten Hardware komplett auf IS-IS-SR migriert, und erst danach werden die Kisten getauscht. Jeder Schritt lässt sich einzeln zurückdrehen, und das Netz kann zwischen den Schritten beliebig lange so laufen.
 
Das Ganze habe ich vorher in Containerlab mit einem Ring aus virtuellen Junos-Routern durchgespielt. Ein Ring deshalb, weil TI-LFA in einer Kette schlicht nichts zu rechnen hat. Und zwar nicht nur den Endzustand, sondern jeden Zwischenzustand – denn die fährt man in Produktion wochenlang.
 
### SRGB und SIDs
 
Der SRGB sollte auf allen Routern identisch sein. Unterschiedliche funktionieren zwar auch (jeder Router swappt dann halt auf das Label des Nachbarn, siehe [hier](https://blog.ipspace.net/2026/08/sr-mpls-multivendor/)), aber viel Spaß beim Troubleshooting. EOS nimmt ab Werk die Basis `900000`, also habe ich unter Junos einfach dasselbe konfiguriert. Vorher aber mit `show mpls label usage` prüfen, dass der Bereich nicht schon von RSVP belegt ist.
 
Der Node-SID-Index ist bei mir `100 + letztes Oktett der Loopback`. `192.0.2.3` bekommt also Index `103` und damit Label `900103`. Ersetzt später ein neuer Router `rtr-03`, übernimmt er Loopback und SID, und für den Rest des Netzes ändert sich nichts.
 
### IS-IS neben OSPF
 
Zuerst kommt IS-IS parallel zu OSPF auf alle Core-Links. Unter Junos hat OSPF intern die Präferenz 10, IS-IS Level 2 die 18. OSPF gewinnt also, IS-IS läuft nur mit. Die Metriken einfach 1:1 aus OSPF übernehmen.
 
```
set interfaces lo0 unit 0 family iso address 49.0001.1920.0000.2001.00
set interfaces et-0/0/0 unit 0 family iso
set interfaces et-0/0/0 unit 0 family mpls
set protocols isis level 1 disable
set protocols isis level 2 wide-metrics-only
set protocols isis interface et-0/0/0.0 point-to-point
set protocols isis interface et-0/0/0.0 level 2 metric 10
set protocols isis interface lo0.0 passive
set protocols mpls interface et-0/0/0.0
```
 
### SR und TI-LFA einschalten
 
Dann SR und TI-LFA dazu ([SRGB](https://www.juniper.net/documentation/us/en/software/junos/segment-routing/topics/example/example-configuring-spring-srgb.html), [TI-LFA](https://www.juniper.net/documentation/us/en/software/junos/segment-routing/topics/example/example-configuring-ti-lfa-using-spring-is-is.html)):
 
```
set protocols isis source-packet-routing srgb start-label 900000
set protocols isis source-packet-routing srgb index-range 65536
set protocols isis source-packet-routing node-segment ipv4-index 101
set protocols isis backup-spf-options use-post-convergence-lfa
set protocols isis interface et-0/0/0.0 level 2 post-convergence-lfa node-protection
```
 
Die `index-range` sollte man gegen die eigene Junos-Version prüfen. Für ein kleines Backbone tut es auch ein deutlich kleinerer Bereich, dann aber auf EOS denselben setzen.
 
Jetzt tauchen in `inet.3` neben den RSVP-Routen auch `L-ISIS`-Routen auf. RSVP hat aber Präferenz 7 ([Doku](https://juniper.net/documentation/en_US/junos13.2/topics/reference/configuration-statement/preference-edit-protocols-mpls.html)) und gewinnt. Im Forwarding ändert sich also noch gar nichts. Kurz prüfen, ob alle Router ihre Node-SID announcen:
 
```
show isis overview
show isis database extensive | match "Node SID"
show route table mpls.0 protocol isis
show isis backup coverage
```
 
### OSPF raus aus dem Rennen
 
Jetzt wird OSPF schlechter gemacht als IS-IS:
 
```
set protocols ospf preference 20
```
 
Vorher aber unbedingt mit `show ted database` schauen, ob die TED auch die IS-IS-Infos hat. Sonst finden die RSVP-LSPs nach dem Abschalten von OSPF keinen Pfad mehr. IS-IS-TE ist unter Junos per Default an ([Doku](https://juniper.net/documentation/en_US/junos13.1/topics/reference/configuration-statement/traffic-engineering-edit-protocols-isis.html)), prüfen schadet trotzdem nicht.
 
### Der große Moment
 
Die eigentliche Migration ist dann eine Zeile pro Router:
 
```
set protocols mpls preference 20
```
 
RSVP hat jetzt 20, L-ISIS 14 – BGP löst seine Next-Hops ab sofort über SR auf. Die RSVP-LSPs laufen weiter und sind der Rollback. Dass zwischendurch der Hinweg über SR und der Rückweg noch über RSVP läuft, ist egal.
 
So sieht das dann aus:
 
```
192.0.2.4/32   *[L-ISIS/14] metric 10
                 >  to 198.51.100.1 via et-0/0/0.0
                    to 198.51.100.5 via et-0/0/1.0
                [RSVP/20/1] metric 10
                 >  to 198.51.100.1 via et-0/0/0.0, label-switched-path rtr-03-to-rtr-04
192.0.2.6/32   *[L-ISIS/14] metric 100
                 >  to 198.51.100.9 via et-0/0/2.0
                    to 198.51.100.1 via et-0/0/0.0, Push 900106, Push 900104(top)
```
 
L-ISIS ist aktiv, und für `192.0.2.6` hat TI-LFA einen Backup-Pfad mit zwei Labels berechnet. Apropos Labels: Jedes kostet 4 Byte, also die MTU im Auge behalten.
 
Wenn alles ein paar Tage sauber läuft, fliegt der Altbestand raus:
 
```
delete protocols mpls label-switched-path
delete protocols rsvp
delete protocols mpls preference
delete protocols ospf
```
 
Monitoring nicht vergessen – LSP-Status gibt es jetzt nicht mehr.
 
### Neue Hardware
 
Ab hier ist es nur noch IS-IS-SR-Interop. Der EOS-Router bekommt Loopback und SID des Routers, den er ersetzt:
 
```
mpls ip
!
interface Ethernet1/1
   mtu 9214
   no switchport
   ip address 198.51.100.2/31
   ipv6 enable
   mpls ip
   isis enable BACKBONE
   isis circuit-type level-2
   isis metric 10
   isis network point-to-point
!
interface Loopback0
   ip address 192.0.2.3/32
   isis enable BACKBONE
   isis passive
   node-segment ipv4 index 103
!
router isis BACKBONE
   net 49.0001.1920.0000.2003.00
   is-type level-2
   router-id ipv4 192.0.2.3
   !
   address-family ipv4 unicast
      fast-reroute ti-lfa mode node-protection
   !
   segment-routing mpls
      no shutdown
```
 
Stolpersteine zwischen Junos und EOS:
 
- **MTU:** Junos zählt den Ethernet-Header mit, EOS nicht. Passt die IP-MTU nicht, kommt zwar die Adjacency hoch, aber die LSPs bleiben hängen.
- **Metriken:** auf beiden Seiten nur Wide Metrics.
- **Netzwerktyp:** beidseitig point-to-point.
- **SRGB:** identisch. Weicht man vom EOS-Default ab, setzt man ihn dort mit `mpls label range isis-sr`.
Der Tausch selbst läuft dann so: Overload-Bit auf dem alten Router setzen (`set protocols isis overload`), damit der Transit drumherum läuft. Dann Kisten tauschen, den neuen Router mit Overload-Bit hochfahren und prüfen. Erst danach das Overload-Bit entfernen. Was direkt am PE hängt, ist in der Zeit natürlich weg, also Wartungsfenster einplanen.
 
Prüfen auf EOS:
 
```
show isis neighbors
show isis segment-routing global-blocks
show isis segment-routing prefix-segments
show mpls label ranges
```
 
Mehr zu IS-IS-SR auf EOS findet man [hier](https://www.arista.com/en/um-eos/eos-is-is).
 
Am Ende hat man ein Protokoll weniger, deutlich weniger Zustand im Netz, ECMP und Backup-Pfade, die dem Pfad nach der Konvergenz folgen. Und der Rollback war bei jedem Schritt genau eine Zeile.
 
Goodbye RSVP. :)
